# Connecting a project to the shared server infrastructure

This document describes **only how a project plugs into the shared infrastructure** it is deployed on:
what is provided, how to reach it, the limits it imposes, and what a deployable project must look like.
It says nothing about how to design or write the project itself (language, framework, structure,
testing are the project's own business). Everything below is a requirement unless marked "optional".

The infrastructure already runs shared PostgreSQL (behind PgBouncer), Redis, RabbitMQ, an edge nginx
and an OpenTelemetry / Prometheus / Tempo / Grafana stack. A project must **use** them and must not
start its own databases, brokers or reverse proxies.

## 1. What is provided

| Need | Where (inside the Docker network `infra`) | Env var |
|---|---|---|
| PostgreSQL 18 | host `pgbouncer`, port `5432` (transaction pooling; never connect to Postgres directly) | `DATABASE_URL` |
| Redis 8 | host `redis`, port `6379`; ACL user limited to keys `<app>:*` | `REDIS_URL`, `REDIS_KEY_PREFIX` |
| RabbitMQ 4 | host `rabbitmq`, port `5672`; own vhost and user | `AMQP_URL` |
| Traces and metrics | OTLP to `otel-collector`: gRPC `4317`, HTTP `4318` | `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_*` |
| Public HTTP | shared nginx routes by `Host` header to the project's containers | n/a |

Credentials are generated by the infra owner (`scripts/new-project.sh`) into an env file on the
machine that runs the infrastructure: `<APPS_DIR>/<app>/.env` (`/srv/apps/<app>/.env` on the server).
The project reads **all** of these values from environment variables, never hardcodes or commits them,
and ships an `.env.example` that lists only the variable names. The generated file contains:

```
DATABASE_URL, REDIS_URL, REDIS_KEY_PREFIX, AMQP_URL,
OTEL_EXPORTER_OTLP_ENDPOINT, OTEL_EXPORTER_OTLP_PROTOCOL, OTEL_RESOURCE_ATTRIBUTES, OTEL_LOGS_EXPORTER
```

Set `OTEL_SERVICE_NAME` per service in the compose file.

## 2. Rules imposed by the shared environment

1. **Unique, prefixed service names.** All projects share one Docker network and a service name is its
   DNS name. Prefix every compose service and image with the app name (`shop-api`, `shop-web`,
   `shop-worker`); otherwise two projects with an `api` service receive each other's traffic.
   Reserved names: `postgres`, `pgbouncer`, `redis`, `rabbitmq`, `nginx`, `otel-collector`,
   `prometheus`, `grafana`, `tempo`.
2. **No published ports** (`ports:` is not allowed). nginx reaches containers over the `infra` network.
3. **Resource limits on every service** (`mem_limit`, `cpus`). The machine is small (4 cores, 8 GB) and
   shared; an unlimited container can take everything down.
4. **No state in the container filesystem.** Run with a read-only root filesystem. Persistent files
   (uploads, ...) go to a bind mount under `/srv/data/apps/<app>/` (created by `new-project.sh`, owned
   by uid 65532); scratch space is `tmpfs`.
5. **Run as uid 65532, non-root**, with `cap_drop: [ALL]` and `no-new-privileges`.
6. **Do not rely on start order.** Compose cannot express dependencies across projects, so the infra
   may come up after the project. Connect to Postgres/Redis/RabbitMQ with retry and backoff, at startup
   and after disconnects.
7. **Health endpoint.** Expose `GET /healthz` returning 200 while the process is alive (do not check
   dependencies in it). It is used by the compose healthcheck and by the external uptime probe.
8. **Logs go to stdout/stderr**, preferably one JSON object per line. There is no log backend and no
   log files; do not export OTLP logs (`OTEL_LOGS_EXPORTER=none` is already set).
9. **Configuration only through environment variables**: the same image must run on any machine.
10. **Image tags are immutable**: `<app>-<service>:<git-sha>`, never `latest`.

## 3. Using each component

### PostgreSQL (through PgBouncer, transaction pooling)

* Connect with `DATABASE_URL` to `pgbouncer:5432`. You get your own database and role; you cannot
  connect to other projects' databases.
* Limits: PgBouncer keeps ~10 server connections (+3 reserve, 25 max) per database; the role is capped
  at 40 connections. Client-side pools of up to ~20 connections per service are fine (PgBouncer
  multiplexes them). Do not size pools to "all connections you may ever need".
* Transaction pooling means a client does not keep the same server connection between transactions.
  Therefore do not use: session-level `SET` (use `SET LOCAL` in a transaction), session-level advisory
  locks (transaction-level ones are fine), `LISTEN/NOTIFY`, temporary tables or cursors that outlive a
  transaction. Protocol-level prepared statements are supported.
* **Migrations**: use a migration tool/mode that does not depend on session-level locks (a
  session-level advisory lock is unsafe through PgBouncer). Run migrations as a separate one-shot step
  (e.g. the same image with a `migrate` command), not on every replica boot. Direct superuser access
  for the infra owner exists only on the server at `127.0.0.1:5432` (via SSH tunnel).
* Use per-query timeouts; `statement_timeout` can be set per role on request.

### Redis

* Connect with `REDIS_URL`. Single logical DB (`/0`); isolation is by key prefix plus ACL.
* **Every key must start with `REDIS_KEY_PREFIX`** (e.g. `shop:`), including Pub/Sub channels. Other
  keys are rejected.
* **Every cache key needs a TTL.** Eviction policy is `volatile-lru`: only keys with a TTL are evicted.
  A key without TTL is never evicted, and when memory (384 MB total, shared) is full, writes fail.
  Data that must not expire belongs in PostgreSQL.
* The ACL denies admin/dangerous commands (`KEYS`, `FLUSHALL`, `FLUSHDB`, `CONFIG`, `DEBUG`,
  `SHUTDOWN`, ...). Use `SCAN` with a prefix instead of `KEYS`.

### RabbitMQ

* Connect with `AMQP_URL` (it already contains your vhost). You have full rights inside your vhost only.
* Limits per vhost: 100 connections, 500 queues. Channels are capped at 256 per connection.
* The broker blocks publishers when it reaches its memory watermark (300 MB total, shared), so keep
  messages small and make sure queues are consumed. Handle connection/channel close events by
  reconnecting and re-declaring topology.

### OpenTelemetry (traces and metrics)

* Export OTLP to `OTEL_EXPORTER_OTLP_ENDPOINT` (`http://otel-collector:4317`, gRPC; HTTP is on `4318`).
  Take the service name and resource attributes from `OTEL_SERVICE_NAME` / `OTEL_RESOURCE_ATTRIBUTES`.
* **Do not sample in the application** (parent-based, always-on): the collector does tail sampling. It
  keeps every error trace, every trace slower than 1 s, and a percentage of the rest. If the
  application samples too, errors and slow requests get lost.
* Use W3C Trace Context (and Baggage) propagation. nginx forwards `traceparent`, so traces continue
  from the edge into the application and between services.
* For the HTTP server use the standard semantic-convention metric `http.server.request.duration`
  (histogram): the "Applications" dashboard (request rate, error ratio, latency per `service.name`)
  is built on it. Use bounded label values only (no user IDs, no raw URLs with IDs, no raw errors).
* Metrics are exported periodically (30 s suggested). Flush telemetry on shutdown.
* Put the trace id in the logs so a log line can be matched to its trace in Grafana (optional but advised).
* Traces are viewed in Grafana (Explore, data source Tempo); retention is 3 days. Metrics 10 days.

### The edge: ArvanCloud CDN and the shared nginx

* TLS ends at the CDN; the application speaks plain HTTP only. Use the `X-Forwarded-Proto` header
  (always set by nginx) to know whether the visitor used HTTPS (secure cookies, absolute URLs, redirects).
* Visitor IP: `X-Real-IP` (set by nginx to the real address). Trust it only because the application is
  reachable solely through nginx.
* nginx adds `X-Request-ID` (kept if the CDN/client sent one) and forwards `Host`, `Upgrade`/`Connection`
  (WebSockets and SSE work). Proxy read timeout is 60 s.
* Request bodies: 20 MB on API routes, 10 MB elsewhere. API routes are rate limited to 30 req/s per
  visitor IP (burst 60, then HTTP 429). Ask the infra owner if a project needs different values.
* CDN caching is controlled by the application's response headers: immutable long-lived caching for
  hashed static assets, `no-cache` for HTML, `private, no-store` for personalised or authenticated
  responses. Do not compress responses (nginx/CDN do).
* For a browser client on a different domain than the API, the API must send correct CORS headers.

## 4. Compose file contract: `deploy/compose.yaml`

The image tag comes from `${TAG}` (set by the ship script); `env_file: .env` is the generated file
(path relative to the compose file on the machine that runs it). Healthcheck `test` must use a tool
that exists in the image (a minimal image may need a built-in health command).

```yaml
name: shop                      # = app name
services:
  shop-api:
    image: shop-api:${TAG}
    env_file: [.env]
    environment:
      OTEL_SERVICE_NAME: shop-api
    volumes:
      - /srv/data/apps/shop/uploads:/data/uploads     # only if the service stores files
    mem_limit: 256m
    cpus: 1.0
    read_only: true
    tmpfs: [/tmp]
    user: "65532:65532"
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]
    restart: unless-stopped
    stop_grace_period: 15s
    logging: { driver: json-file, options: { max-size: "10m", max-file: "3" } }
    healthcheck:
      test: ["CMD", "<command that checks GET /healthz and exits 0/1>"]
      interval: 10s
      timeout: 3s
      retries: 3
      start_period: 15s
    networks: [infra]

networks:
  infra:
    external: true
```

Every service that talks to the shared infrastructure or is proxied by nginx joins `infra` (and only
`infra`, unless it needs a private network for project-internal traffic). Background workers are just
more services with the same attributes. A client (frontend) container is a service like any other: it
listens on a plain HTTP port, which is the upstream registered with `new-project.sh`.

## 5. Shipping: build locally, deploy over SSH, no registry

`scripts/ship.sh` (from the infra repo; copy it into the project) reads `ship.conf` at the project root:

```bash
APP=shop                                     # same name that was given to new-project.sh
SSH_HOST=deploy@my-server                    # or "local" when the infrastructure runs on this machine
COMPOSE_FILE=deploy/compose.yaml
IMAGES=("api=./backend" "web=./client")      # service=context[:dockerfile] -> images shop-api, shop-web
# REMOTE_DIR=/srv/apps/shop                  # default; with SSH_HOST=local set <APPS_DIR from the infra .env>/<app>
```

It builds `linux/amd64` images, tags them with the git SHA, streams them to the server
(`docker save | ssh | docker load`), runs `docker compose up -d --wait`, and **rolls back to the previous
tag automatically** if the new containers do not become healthy. Commit before shipping (a dirty tree
gets a `-dirty<timestamp>` tag). With `SSH_HOST=local` nothing is copied or sent over SSH; domains for
local use are `<app>.localhost` and `api.<app>.localhost`.

## 6. Onboarding (needs the infra owner once per project)

1. Pick the app name (`^[a-z][a-z0-9-]{1,30}$`) and the project's own domains.
2. The infra owner runs, in the infra repo, `make new-project` (or
   `scripts/new-project.sh <app> --client-domain ... --client-upstream http://<app>-web:<port> --api-domain ... --api-upstream http://<app>-api:<port>`;
   `--api-path /api` serves the API under the client domain instead). It creates the database, Redis
   user, RabbitMQ vhost, nginx server blocks, uptime probes, the uploads directory and the env file.
3. Point the domains at the server in the CDN panel (HTTP origin, port 80).
4. Ship with `scripts/ship.sh`.

## 7. Checklist

- [ ] Compose services/images are prefixed with the app name; no published ports; joined only to `infra`
- [ ] `mem_limit` + `cpus`, healthcheck, read-only fs, uid 65532, `cap_drop: [ALL]`, `no-new-privileges`
- [ ] All settings from environment variables; `.env.example` lists names only; no secrets committed
- [ ] PostgreSQL through `DATABASE_URL` without session state; migrations safe for transaction pooling
- [ ] Redis keys prefixed with `REDIS_KEY_PREFIX` and given TTLs; RabbitMQ reconnects after failures
- [ ] OTLP to the collector, no application-side sampling, W3C propagation, `http.server.request.duration` emitted
- [ ] Retry/backoff when dependencies are unavailable; graceful stop on SIGTERM within `stop_grace_period`
- [ ] `GET /healthz` exists and does not depend on external services
- [ ] `ship.conf` present; images named `<app>-<service>`
